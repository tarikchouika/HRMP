## 1. خريطة النشر

| البيئة | المنصة | قاعدة البيانات | متى تُستخدم |
|---|---|---|---|
| **سحابية** | Vercel (نشر تلقائي من `main`) + بوابة Cloudflare Pages `fwms-dg8.pages.dev` فوقها (§3.2) | SQLite مؤقت لكل نشر معاينة + خدمة قاعدة سحابية متوافقة عند الإنتاج (Turso/libSQL أو Vercel Postgres عند اعتماد صاحب المشروع) | العرض، التطوير، تجربة الوظائف |

## 2. Vercel — الإعداد (محدَّثة في v0.13.1 — راجع CHANGELOG وWORKLOG)

> **⚠️ تغيير معماري نافذ منذ v0.13.1 (علاج بلاغ المالك 2026-10-25 «لا أستطيع تسجيل الدخول لواجهة المنصة المنشورة في ڤيرسيل»):** نشر Vercel صار **بوابة عكسية إلى الخادم المرجعي** (`fwms.tarikc.workers.dev` — الهاتف عبر النفق) عبر `rewrites` catch-all في `next.config.ts` تعمل حصرًا عند `VERCEL=1` — نفس معمارية hrmp.pages.dev (§3.2). النتيجة: كلمة مرور واحدة وبيانات واحدة وسلوك واحد على كل الروابط (التطبيق / pages.dev / vercel.app)، والوثائق المولَّدة عبر hrmp.vercel.app تُحفظ في قاعدة الإنتاج فعلًا. آلية «لقطة المعاينة» (§2.1) صارت **خارج الخدمة افتراضيًا** وتعود بضبط `HRMP_VERCEL_DIRECT=1`.
>
> **مفاتيح تشغيلية للبوابة:** `HRMP_REFERENCE_ORIGIN` (افتراضي: `https://fwms.tarikc.workers.dev`) يغيّر الأصل دون كود · `HRMP_VERCEL_DIRECT=1` يوقف البوابة ويعيد تشغيل التطبيق محليًا على Vercel · حد حجم طلب دوال Vercel ‏4.5MB (رفع وثائق هوية الباحثين أكبر منه يستمر عبر pages.dev/التطبيق) · الهاتف يلزمه سحب نفس إصدار المستودع (البوابة تعكس نسخته) · سلوك الهاتف والتطوير لم يتغير قيد أنملة (البوابة شرطها `VERCEL=1`).

1. ادخل [vercel.com](https://vercel.com) → **Add New Project** → استورد `tarikchouika/HRMP` من GitHub.
   (**hrmp.vercel.app**: المشروع باسم `hrmp` **قائم وحي** — أنشأه المالك وربطه بالمستودع، وكل push إلى main ينشر عليه تلقائيًا (تحقّق حي 2026-10-24: v0.13.0 مع صفحات /jobs). البوابة القديمة fwms-orpin.vercel.app لم تعد قائمة بعد الربط الجديد.)
2. إعدادات البناء تُكتشف تلقائيًا (Next.js). لا حاجة لتخصيص.
3. متغيرات البيئة (Production + Preview) — **كلها اختيارية منذ v0.9.2** (آلية اللقطة أدناه تعمل بلا أي منها):
   - `DATABASE_URL` — إن غاب أو أشّر لملف غير موجود: تُستعمل **لقطة معاينة** تلقائيًا. وإن ضُبط بقاعدة سحابية حقيقية (Turso/Postgres) يُحترم ولا يُمس.
   - `AUTH_SECRET` — سر جلسات JWT (توليد: `openssl rand -base64 48`). إن غاب على نشر Vercel: احتياط معاينة معلن مع تحذير في السجل — **إلزامي حقيقي عند أي استخدام إنتاجي سحابي**.
   - `NEXTAUTH_URL` — نطاق النشر (اختياري).
4. Deploy. كل push إلى `main` = نشر تلقائي. كل PR = رابط معاينة.
5. أضف نطاق Cloudflare إلى المشروع (Step 3) واتبع تعليمات DNS.

### 2.1 آلية «لقطة المعاينة» (نافذة منذ v0.9.2 — **خارج الخدمة افتراضيًا منذ v0.13.1**: تُفعَّل بـ `HRMP_VERCEL_DIRECT=1` — جذر إصلاح «لا أستطيع الدخول»)

> **المشكلة التي كانت:** نشر Vercel بلا قاعدة فعلية (`database:error` + `/login` 500 + دخول `internal_error`) — بيئة serverless بلا ملف قاعدة ولا متغير صالح.
>
> **الحل:** لقطة قاعدة جاهزة `infra/vercel/preview.db` (migrations كاملة + بذور العرض نفسها: 7 مستخدمين / 32 قاعدة أجور / مالك منصة) تُرفع مع المستودع، تضمّنها `outputFileTracingIncludes` (next.config.ts) **لكل مسار يلمس القاعدة**، وعند الإقلاع (`src/lib/db.ts`) تُنسخ إلى `/tmp` (نظام الملفات الوحيد القابل للكتابة على Vercel) ويُوجَّه `DATABASE_URL` إليها — **حصرًا عند `VERCEL=1`**: الهاتف والتطوير لا يتغير سلوكهما قيد أنملة، وأي `DATABASE_URL` سحابي حقيقي لا يُمس.

- **عقد البيانات:** مؤقتة لكل «نسخة مثيل» (instance) — تُصفَّر مع كل نشر جديد. هذا عقد **معاينة** (SPEC §7 + §1 أعلاه)؛ الإنتاج الحقيقي يظل على الخادم المحلي، والإنتاج السحابي الحقيقي قرار مالك عند أول عميل (قاعدة سحابية متوافقة).
- **إعادة التوليد عند أي تغيير في المخطط/البذور:** `bash scripts/regen-preview-db.sh` (تحقق سلامة إجباري عبر Prisma — يرفض رفع لقطة معطوبة) ثم التزام.
- **الاعتماديات التجريبية:** دخول المعاينة على `fwms-orpin.vercel.app` بحسابات البذور (مثل `owner@fwms.local` / `admin@demo.ma`) — **كلمة مرورها ليست `Fwms#2026` ولا أي قيمة منشورة**: اللقطة تُعاد توليدها بـ `scripts/regen-preview-preserve-passwords.sh` الذي يستعيد بصمات كلمات المرور السابقة، فهي بيد المالك وحده ولا تُكتب في المستودع أبدًا (تحقّق حي 2026-10-24: `Fwms#2026` ⇐ 401 على البوابات الثلاث كلها).
- **قاعدة نافذة (بلاغ المالك 2026-10-24 «لا أستطيع الدخول من تطبيق أندرويد» + بلاغ 2026-10-25 «لا أستطيع الدخول على ڤيرسيل»):** بيانات اعتماد الإنتاج تعيش **في قاعدة الهاتف حصرًا** — التطبيق وبوابة workers.dev وpages.dev و(منذ v0.13.1) vercel.app كلها على تلك القاعدة عبر البوابات العكسية. لا لقطة معاينة معزولة بكلماتها بعد الآن (البوابة نافذة افتراضيًا)، ولا تُوحَّد بصماتها مع الإنتاج ولا تُرفع للمستودع (أي توحيد = تسريب بيانات اعتماد الإنتاج إلى مستودع عام). إن فُقدت كلمة المالك على الهاتف فالعلاج الموثّق: `infra/termux/reset-owner-password.sh` (تشغيل ذاتي من المالك داخل Termux — يضبط كلمة يختارها بنفسه ويبطل كل الجلسات القديمة).
- **عند أول استخدام إنتاجي سحابي:** اضبط `AUTH_SECRET` حقيقيًا وقاعدة سحابية حقيقية من لوحة Vercel — واحتياط المعاينة يظل غير مُفعَّل أصلًا لأن السر مضبوط.

## 3. Cloudflare — الإعداد

**معرّف الحساب:** `758fcc827f3338772847c28391b6c6c3` — **رمز الـ API يُحفظ في `.env`/أسرار المنصات فقط ولا يُكتب في أي ملف مرفوع.**

### 3.1 DNS للنطاق السحابي (Vercel)
في لوحة Cloudflare → DNS → سجلات تشير إلى نطاق Vercel (`cname.vercel-dns.com`) حسب تعليمات Vercel عند إضافة النطاق. وضع الوكيل (Proxy) اختياري.

### 3.2 بوابة الواجهة العامة على Pages — مشروع `fwms` (fwms-dg8.pages.dev) — أُنشئت 2026-10-18

> بطلب صريح من صاحب المشروع («يجب نشر فرونت أند المنصة على Cloudflare: fwms.pages.dev»).
> **الواقع الميداني:** `fwms.pages.dev` محجوز عالميًا لدى طرف ثالث (موقع `lang="th"` قائم قبل الإنشاء) — لا يُملك ولا يُطالب. Cloudflare أسند تلقائيًا **`fwms-dg8.pages.dev`** لمشروعنا المسمّى **`fwms`** (محاولة `PATCH subdomain=fwms` تجاهلها النظام). **لعنوان أنظف لاحقًا:** أضف نطاقًا مخصصًا (Custom Domain) للمشروع من لوحة Cloudflare — يعمل فوق البوابة بلا أي تغيير في الكود.

- **النمط:** Pages Advanced Mode — `_worker.js` (في `infra/cloudflare/fwms-pages/`) يعالج كل الطلبات بوصفه بوابة عكسية إلى أصل Node سليم. تشغيل التطبيق نفسه على workerd غير ممكن (Prisma+SQLite ملفي، bcrypt، sharp، عامل العرض الابنة) — البوابة تحفظ «كود واحد وسلوك واحد» (SPEC §7).
- **الأصل الحالي:** `https://fwms.tarikc.workers.dev` (**بوابة الهاتف/الخادم المرجعي عبر النفق**) — محدَّث 2026-10-23 بأمر المالك وتوكن الحساب، بعد تحقّق الشرط الموثَّق (الهاتف ≥ v0.9.2 — هو الآن v0.12.1). سبب التبديل مقيس: نشر Vercel يعمل على لقطة SQLite مؤقتة في `/tmp` لكل نسخة، فوثيقة مولَّدة عليه تضيع ومسح QR يعطي `not_found` مع أن الرابط يعمل. **الأثر:** الرابط المطبوع على الوثائق (`pages.dev`) يخدم بيانات الإنتاج مباشرةً؛ **والمقابل:** الهاتف صار نقطة الاعتماد لهذه البوابة (إن غاب النفق ⇒ 503). سجل الأصل السابق: `https://fwms-orpin.vercel.app` حتى 2026-10-23.
- **إجراءات الخادم خلف البوابة (درس 2026-10-19 — جولة v0.10.5):** Vercel يستبدل ترويسة `x-forwarded-host` الواردة بقيمته، فلا يرى التطبيق المضيف العام ⇒ حماية CSRF في Next ترفض كل إجراء خادمي عبر البوابة (500/E80) — ومنه مبدّل اللغة. العلاج: `experimental.serverActions.allowedOrigins` في `next.config.ts` يضم `fwms-dg8.pages.dev`. **أي نطاق عام جديد أمام التطبيق (نطاق مخصص للبوابة مثلًا) يجب إضافته إلى القائمة نفسها** — وإلا انكسرت كل الإجراءات الخادمية عليه بصمت.
- **النشر:** `cd infra/cloudflare/fwms-pages && npx wrangler pages deploy public --project-name=fwms --branch=main` — التوكن عبر `CLOUDFLARE_API_TOKEN` حصرًا (متغير بيئة — لا يُكتب في أي ملف).
- **التحقق (§5):** `/_gateway/health` (البوابة ذاتها) ثم `/api/health` ثم `/login` 200 ثم دخول فعلي — كلها مُثبتة حيًّا يوم الإنشاء.

### 3.3 Tunnel للخادم المحلي (الهاتف)

```bash
# على الهاتف (Termux/Ubuntu) — بتنسيق cloudflared:
cloudflared tunnel login
cloudflared tunnel create fwms-local
cloudflared tunnel route dns fwms-local fwms-local.<نطاقك>
cloudflared tunnel run --url http://localhost:3000 fwms-local
```

- ملف الإعداد المرجعي: `infra/cloudflare/tunnel.example.yml` (بلا أسرار).
- الخادم المحلي يصبح متاحًا عبر `https://fwms-local.<نطاقك>` بلا فتح أي منفذ.
- **التحقق الجغرافي للحضور يبقى إلزاميًا في الوضعين** على الخادم نفسه (SPEC §4.2) — النفق مجرد نقل، لا يغيّر قواعد التحقق.

### 3.2-جديدة بوابة المنصة الجديدة hrmp.pages.dev (2026-10-24 — طلب المالك)

> مشروع Cloudflare Pages جديد باسم `hrmp` → **hrmp.pages.dev** — نفس نمط البوابة المعتمد (§3.2): `_worker.js` بوابة عكسية إلى الخادم المرجعي نفسه (fwms.tarikc.workers.dev — الهاتف خلف النفق).
> - المصدر: `infra/cloudflare/hrmp-pages/` (نسخة محدثة من بوابة fwms القائمة التي تبقى حية).
> - النشر: `cd infra/cloudflare/hrmp-pages && npx wrangler pages deploy public --project-name=hrmp --branch=main` عبر `CLOUDFLARE_API_TOKEN`.
> - أصول إجراءات الخادم للنطاقين الجديدين (`hrmp.pages.dev` + `hrmp.vercel.app`) أُضيفت في next.config.ts.
> - بوابات التحقق المطبوعة على الوثائق (qr.ts): أولها hrmp.pages.dev ثم القديمتان الحية.

### 3.4 تطبيق الأندرويد (APK) — البناء الآلي والرابط الدائم (2026-10-19)

> بطلب المالك: «يجب أن يشتغل سير بناء ملف apk بشكل آلي كلما نُشرت نسخة محسّنة أو أي تحديث، وينشئ رابطًا دائمًا لتحميل آخر نسخة».

- **النمط:** غلاف Capacitor (webview) يشير إلى **الخادم المرجعي** حصرًا (`server.url` = `https://fwms.tarikc.workers.dev` افتراضيًا، قابل للتجاوز بمدخل `app_url` عند التشغيل اليدوي) — كود واحد وسلوك واحد (SPEC §7)؛ لا نسخة أندرويد تُصان يدويًا، و`www` مجرد احتياط بلا اتصال يفتح المنصة في المتصفح.
  - **لماذا الخادم المرجعي لا بوابة Vercel (درس مقيس 2026-10-23):** بوابتا `fwms-dg8.pages.dev` و`fwms-orpin.vercel.app` تستلقيان نشر Vercel الذي يعمل على **لقطة SQLite في `/tmp` تُنشأ لكل نسخة**؛ فالوثيقة المولَّدة داخل التطبيق تُكتب في تلك اللقطة المؤقتة ثم **تضيع** (تنزيل/نسخة محدَّثة يفشلان) ويصير مسح QR يعطي «غير حقيقية» (`not_found`) مع أن الرابط يعمل. الخادم المرجعي (الهاتف خلف النفق) هو الموضع الوحيد الذي تُحفظ فيه الوثائق فعلًا. **نتيجة التشغيل:** التطبيق يحتاج النفق قائمًا (كما هو حال كل بيانات الإنتاج أصلًا).
- **تصدير/تنزيل الوثائق داخل التطبيق (2026-10-23):** WebView في أندرويد **لا ينفّذ** `<a download>` على روابط `blob:` (لا `DownloadListener` في الغلاف) فيبدو التصدير صامتًا. العلاج: `src/lib/native-bridge.ts` يكتب الملف في ذاكرة التطبيق (`Filesystem.writeFile` إلى `CACHE` بترميز base64) ثم يفتح **مشاركة النظام** (`Share.share`: حفظ في التنزيلات · فتح ببرنامج PDF · إرسال)، عبر `window.Capacitor.nativePromise` الذي يحقنه الغلاف في الصفحة البعيدة — بلا إضافة أي حزمة `@capacitor/*` إلى حزمة الويب، وبسقوط آمن إلى تنزيل المتصفح إن فشلت المشاركة. الإضافات الثلاث (`status-bar`/`filesystem`/`share`) تُربط عبر `includePlugins` في `capacitor.config.json` (اكتشاف Capacitor يقرأ `dependencies`، والسير يثبّتها `--no-save` ⇒ القائمة الصريحة حتمية).
- **ملء الشاشة مع شرائط النظام (2026-10-23):** نافذة حافة-لحافة (`WindowCompat.setDecorFitsSystemWindows(false)` + شرائط شفافة و`shortEdges` في `styles.xml` بنسختيه النهارية/الليلية) و`MainActivity` يحقن قياسات `WindowInsets` الفعلية بالبكسل في `--fwms-inset-*` على `<html>` بعد كل تحميل صفحة وبعد كل تغيّر (شريط الحالة/التنقّل/الجزّة/لوحة المفاتيح)؛ الويب يستهلكها في إزاحة واحدة على `body` مع `100dvh` و`viewport-fit=cover`، والترويسة الملتصقة تلتصق تحت شريط الحالة. في المتصفح العادي القيم كلها صفر ⇒ لا تغيير في التصميم.
- **التحقق من الأصالة على بوابات النشر (2026-10-23):** كانت الوثائق تُولَّد على الخادم المرجعي والبوابتان على لقطة Vercel التي لا تحتويها ⇒ الحكم `not_found`. **علاج مزدوج:** (أ) **تحقق فدرالي** — عند عدم وجود الوثيقة محليًا تسأل البوابةُ الخادمَ المرجعي (`FWMS_VERIFY_FALLBACK_ORIGIN`، وافتراضيًا `https://fwms.tarikc.workers.dev` عند ضبط `VERCEL=1`) وتنسخ حكمه بمهلة 8 ثوانٍ، وتقدّم حكم `hash_mismatch` المرجعي (تزييف) على `not_found` المحلي؛ (ب) **نُفِّذ تغيير `ORIGIN`** في مشروع Pages إلى الخادم المرجعي (§3.2) فصار الرابطُ المطبوع يخدم بيانات الإنتاج مباشرة. نقطة التحقق تبقى عامة ومحدودة (رقم مرجعي + بصمة) فلا كشف إضافي.
- **رابطان على كل وثيقة (أمر المالك 2026-10-23، محدَّث v0.13.1):** كل وثيقة مصدَّرة (PDF/DOCX/PNG) تطبع **رابطَي تحقق عامّين** — `hrmp.pages.dev` و`hrmp.vercel.app` (تُضبط القائمة بـ`HRMP_PUBLIC_VERIFY_ORIGINS`) — وQR الوثيقة يحمل الأول (pages.dev). (القديمتان fwms-dg8 وfwms-orpin أُزيلتا من الافتراضي ببلاغ المالك 2026-10-25 «يظهر رابط التحقق للنسخة القديمة ولا يظهر رابط ڤيرسيل» — ورابط vercel يعمل فعلًا لأنه صار بوابة إلى المرجعي.)
- **المشغّلات** (`.github/workflows/android-build.yml`): كل push إلى `main` (أي تحديث) + كل وسم `v*` + تشغيل يدوي (بإمكانية تمرير `app_url`). `concurrency` تُلغي البناءات المتقادمة عند توالي الدفعات.
- **الإصدار:** يُقرأ من `src/lib/version.ts` حصرًا (المصدر الوحيد) ويُحقن في Gradle (`versionName` + `versionCode` = major×1000000+minor×10000+patch×100). نفس الإصدار عبر عدة pushes = تحديث نفس الـ Release وأصوله؛ رفع الإصدار = إصدار جديد يصير «الأحدث» تلقائيًا.

## 3.5 مزوّدو رموز التحقق (OTP) لتسجيل الباحثين (2026-10-24)

> «التأكد الألي من رقم هاتفه و الإيمايل» (طلب المالك): الإرسال عبر مزوّدين قابلين للضبط من `.env` — **بلا مزوّد في الإنتاج يرفض الإرسال صراحة (503)** لا حلقة أمنية تُختصر:
> - البريد: `SMTP_HOST/SMTP_PORT/SMTP_SECURE/SMTP_USER/SMTP_PASS/SMTP_FROM` (أي مزوّد SMTP).
> - الهاتف: `SMS_WEBHOOK_URL` + `SMS_WEBHOOK_TOKEN` — POST JSON `{phone, message}` (أي مزوّد SMS أو Webhook).
> - للاختبار المحلي فقط: `OTP_DEV_SHOW_CODE=1` (يعيد الرمز في الواجهة بتحذير — لا يُستعمل في إنتاج حقيقي أبدًا).

## 4. سياسة الأسرار (نافذة)

| السر | أين يُخزَّن | ممنوع |
|---|---|---|
| GitHub PAT | مدير اعتمادات git المحلي فقط (أو GitHub CLI) | ❌ في أي ملف مرفوع |
| Cloudflare API Token | `.env` على الجهاز المخوَّل + أسرار Vercel عند الحاجة | ❌ في الكود/التوثيق |
| Vercel Token | أسرار GitHub Actions عند أتمتة النشر | ❌ في الكود |
| `AUTH_SECRET` | `.env` / متغيرات Vercel | ❌ في الكود |
| روابط قاعدة الإنتاج | متغيرات المنصة | ❌ في التوثيق |

**عند اشتباه تسريب:** إبطال فوري من لوحة الجهة → تنظيف تاريخ Git إن لزم → تدوير كل الأسرار → إبلاغ في `docs/WORKLOG.md`.

**الدفع من بيئة بلا مدير اعتمادات** (بيئة التطوير السحابية أو Termux):
```bash
FWMS_GITHUB_TOKEN=ghp_xxxxxxxxxxxx ./scripts/push.sh   # يدفع main + الوسوم
```
التوكن كمتغير بيئة فقط — يُبطل فور انتهاء الحاجة، ولا يُخزَّن في أي ملف.

## 6. الانتقال بين البيئتين (SPEC §7) — إجراء مُختبَر (المرحلة 8)

> **مُختبَر فعليًا 2026-10-17** (جلسة المرحلة 8): نسخة عبر VACUUM INTO ثم فحص تطابق
> (quick_check + 35 جدولًا × 401 صفًا متطابقة) ثم إقلاع البيئة الثانية كخادم إنتاج standalone ثم
> تطابق دخول + قراءات API (شركات/تدقيق/مسارات) — الدليل في WORKLOG قيد المرحلة 8.

**محلي ← عام (والعكس):**

```bash
# 1) نسخة احتياطية سليمة أثناء التشغيل + فحص تطابق آلي (أداة موثقة بالمستودع)
bun scripts/transfer-between-env.ts <المصدر.db> <الهدف.db>
#    أو على الهاتف بـ sqlite3: sqlite3 المصدر.db "VACUUM INTO 'الهدف.db'" + PRAGMA quick_check

# 2) شغّل البيئة الجديدة على النسخة
#    (الخادم المستقل يقرأ PORT/HOSTNAME/DATABASE_URL من البيئة — درس WORKLOG)
env NODE_ENV=production PORT=<منفذ> HOSTNAME=0.0.0.0 \
  DATABASE_URL=file:<المسار الكامل للهدف.db> \
  AUTH_SECRET=<openssl rand -hex 32> \
  bun .next/standalone/server.js

# 3) تحقق: /api/health + دخول مستخدم بذور + مقارنة عدد السجلات لكل جدول
#    (سكربت transfer-between-env يقوم بالمقارنة آليًا)
```

- **تنبيه مهم:** لا يُنقل `AUTH_SECRET` مع القاعدة — للبيئة الجديدة سرها الخاص (تدوير مستقل).
- الأداة المرجعية للنسخ اليومية: `infra/termux/backup.sh` (المساعد الثاني — Online Backup API + quick_check) —
  والإجراء أعلاه للنقل الكامل بين بيئتين.
- كل نقل يُوثّق في WORKLOG (المصدر/الهدف/البصمات/من نفّذ).

### ملاحظات أداء الخادم المحلي (مُنفّذة المرحلة 8)

- لوغ استعلامات Prisma معطل في الإنتاج (`src/lib/db.ts`) — كان يطبع كل استعلام على الهاتف.

  واقتراح فهارس إن لزم (ملكية المخطط له — عبر WORKLOG).
